## Roadmap Summary

Agent Arena is a 20+ week build from CLI prototype to spectator platform. The critical insight: **Phase 0 can be built in ~3 weeks and already produces value** — it's essentially a productized version of the manual hackathon workflow. Each subsequent phase adds a layer (UI, multi-model, synthesis, spectator) with a go/no-go gate.

**Total estimated effort:** 1–2 engineers (Phase 0–1), scaling to 3–4 (Phase 2+)

---

## Phase 0: CLI Orchestrator — "Productize the Hackathon" (Weeks 1–3)

**Objective:** A working CLI tool that runs two Claude teams with different personas against a structured brief, logs events, judges results, and outputs a winner. No UI. Terminal only.

### Milestone 0.1 — Core Orchestrator Engine (Week 1)

- Build competition state machine (DRAFT → CONFIGURED → LAUNCHING → RUNNING → TIME_UP → COLLECTING → JUDGING → SCORED → COMPLETE)
- Implement brief parser (YAML/JSON input with problem statement, constraints, deliverables, rubric)
- Build clock manager (configurable time limits, graceful shutdown signals)
- Implement event logger (structured JSON events to file — the event stream prototype)
- Design universal event schema (eventId, competitionId, teamId, timestamp, type, payload, metadata)
- **Deliverable:** State machine runs through full lifecycle with stub teams; events logged to JSON file

### Milestone 0.2 — Claude Adapter + Sandbox (Week 1–2)

- Build Claude Code adapter (spawn Claude Code process, inject brief as system prompt, capture streaming output)
- Implement event normalization (map Claude Code tool calls, file ops, reasoning to universal event schema)
- Build lightweight sandbox (Docker container per team with isolated filesystem, shared brief, event emitter)
- Implement persona injection (different system prompts for each team — same model, different cognitive frames)
- Build deliverable collector (extract final artifacts from each sandbox filesystem)
- **Deliverable:** Two Claude teams can run simultaneously in isolated Docker containers, events streaming to log

### Milestone 0.3 — Judging Engine (Week 2–3)

- Build rubric scoring system (weighted criteria from brief, numeric scores per criterion)
- Implement AI cross-judge (Team A's work judged by a separate Claude instance, Team B's similarly)
- Build automated scorer (basic checks: deliverable exists, word count, structure validation)
- Implement score aggregation (average across judges, outlier detection, final ranking)
- Build results reporter (terminal output: scores per criterion, overall ranking, judge commentary)
- **Deliverable:** Full competition runs end-to-end: brief → two teams → deliverables → judging → ranked results

### Milestone 0.4 — Brief Templates + First Real Run (Week 3)

- Create brief template library (3–5 templates: architecture decision, strategy proposal, code challenge, creative brief, analysis)
- Build competition config presets (Sprint: 15 min, Hackathon: 1–2 hrs)
- Run first real competition (re-run the Monday Pulse hackathon through the CLI tool)
- Compare CLI-orchestrated results to manual hackathon results
- Document learnings and adapter edge cases
- **Deliverable:** CLI tool used on a real problem; results validated against manual process

### 🚦 Gate 0 — Go/No-Go for Phase 1
| Criterion | Measure |
|-----------|---------|
| End-to-end execution | Competition completes without crashes across 5 test runs |
| Event capture fidelity | ≥90% of meaningful agent actions captured in event stream |
| Judge quality | Cross-judge scores correlate with human ranking in 3/3 test cases |
| Time to run | Full competition (brief → results) completes within 2x the time budget |
| Real-world validation | Monday Pulse re-run produces results comparable to manual hackathon |

**Decision maker:** Platform owner
**Timeline:** End of Week 3

## Phase 1: Multi-Model + Web Arena UI (Weeks 4–8)

**Objective:** Add Codex and Gemini adapters. Build the React Arena UI with live lane view and WebSocket streaming. First version where you watch AI teams compete from a browser.

### Milestone 1.1 — Model Adapter Framework (Week 4)

- Design adapter interface (standard contract: injectBrief, startExecution, emitEvent, collectDeliverables, shutdown)
- Build Codex CLI adapter (spawn Codex agent, capture events, normalize to universal schema)
- Build Gemini adapter (interface with Gemini agent SDK, capture events, normalize)
- Implement adapter registry (plug-and-play model registration, runtime adapter selection)
- Build adapter health checks (connection verification, model availability, latency baseline)
- **Deliverable:** 3-model adapter framework; any adapter can be swapped into any team slot

### Milestone 1.2 — Event Bus + WebSocket Bridge (Week 4–5)

- Set up NATS JetStream (event bus for real-time event distribution)
- Build sandbox → NATS event publisher (each sandbox pushes events to NATS subjects per team)
- Build NATS → WebSocket bridge (server-side: consume NATS, fan out to connected clients)
- Implement event persistence (NATS → PostgreSQL event store for replay)
- Build event replay from store (re-emit historical events in sequence for replay viewer)
- **Deliverable:** Events flow from sandbox → NATS → WebSocket → browser in real time

### Milestone 1.3 — Arena Web UI (Week 5–7)

- Build React application shell (Next.js, TailwindCSS, dark theme matching concept doc aesthetic)
- Implement Brief Builder (structured form: problem, constraints, deliverables, rubric, time, team config)
- Build Arena View — Lane Visualization (split-screen lanes per team, live event feed per lane)
- Implement event rendering (icons, timestamps, expandable detail for each event type)
- Build competition controls (Launch, Pause, Resume, Cancel buttons wired to orchestrator)
- Build scoreboard view (post-judging: scores per criterion, ranking, judge commentary)
- Implement basic auth (magic-link or API key for operator access)
- **Deliverable:** Operator can create brief → configure teams → launch → watch live → see results, all in browser

### Milestone 1.4 — Sandbox Upgrade (Week 6–8)

- Migrate from Docker to Firecracker microVMs (faster boot, better isolation, lower overhead)
- Implement resource governance (token budget tracking, API call counters, sub-agent spawn caps)
- Build budget visualization (real-time resource gauges per team in Arena UI)
- Implement graceful shutdown protocol (TIME_UP → "wrap up" signal → 30s grace → force collect)
- Add sandbox health monitoring (heartbeat checks, crash detection, automatic event on failure)
- **Deliverable:** Production-grade sandboxes with governance; resource usage visible in Arena UI

### 🚦 Gate 1 — Go/No-Go for Phase 2
| Criterion | Target |
|-----------|--------|
| 3-model competition | Claude vs Codex vs Gemini runs successfully end-to-end |
| Live Arena UI | Operator can observe all 3 teams in real time with < 2s event latency |
| Adapter reliability | Each adapter completes 5/5 test competitions without adapter-layer failures |
| Brief Builder | Non-technical operator can create and launch a competition in < 10 minutes |
| Resource governance | Token budgets enforced; no runaway costs in any test run |

**Decision maker:** Platform owner + first beta operators
**Timeline:** End of Week 8

## Phase 2: Synthesis + Intelligence Layer (Weeks 9–14)

**Objective:** Build the synthesis engine (the killer feature), multi-judge panel, competition format presets, and replay viewer. This is where Agent Arena becomes genuinely valuable.

### Milestone 2.1 — Multi-Judge Panel (Week 9–10)

- Build judge orchestrator (spawn N judges, distribute deliverables, collect scores, aggregate)
- Implement AI cross-judge (Model A judges Model B; no self-scoring)
- Implement neutral AI judge (a model not competing evaluates all submissions)
- Build automated scoring (code compilation, document validation, structure checks, math verification)
- Implement human judge interface (operator scores in Arena UI, can override AI judges)
- Build outlier detection (flag dramatically different scores, request re-evaluation)
- **Deliverable:** Competitions judged by 3+ judges with weighted rubric; operator can review and override

### Milestone 2.2 — Synthesis Engine (Week 10–12)

- Build auto-synthesis mode (take top 2–3 solutions, identify best elements, generate hybrid)
- Build guided synthesis mode (operator selects which elements to combine, AI executes merge)
- Build competitive synthesis mode (remaining teams get competitor solutions, produce improved hybrid)
- Implement synthesis transparency (output annotates which ideas came from which team and why)
- Build synthesis quality scoring (judge the synthesis against original submissions)
- **Deliverable:** After any competition, operator can run synthesis and get a hybrid solution better than any individual

### Milestone 2.3 — Competition Format Presets (Week 11–13)

- Implement Sprint format (15–30 min, streamlined brief, speed scoring bonus)
- Implement Hackathon format (1–4 hrs, complex deliverables, multi-part judging)
- Implement Relay Race format (Team A → handoff → Team B continues; test interoperability)
- Implement Red vs Blue format (build round → attack round → score; adversarial)
- Implement Bracket/Tournament format (multi-round elimination)
- Implement A/B Experiment format (same model, different configs, controlled comparison)
- Build format configuration UI (preset selector with customizable parameters)
- **Deliverable:** Operator can choose format from 6 presets or customize; each runs correctly

### Milestone 2.4 — Replay Viewer (Week 12–14)

- Build replay engine (reconstruct visual state from event stream at any timestamp)
- Implement timeline scrubber (drag to any point, variable playback speed: 1x, 2x, 4x, 10x)
- Build team zoom (click a team to focus on their lane, see full detail)
- Implement event filtering in replay (show only: tool calls, file ops, reasoning, all)
- Build replay export (shareable URL with read-only replay access)
- **Deliverable:** Any past competition can be replayed with full fidelity; scrub to any moment

### Milestone 2.5 — Analytics Foundation (Week 13–14)

- Build competition analytics dashboard (per-competition: timing, token usage, event counts, scores)
- Implement model performance tracker (across competitions: win rate by model, by problem type)
- Build the meta-dataset schema (competition type × model × outcome → performance patterns)
- Implement analytics API (query model performance, competition history, trend data)
- **Deliverable:** After 10+ competitions, analytics show which models win which problem types

### 🚦 Gate 2 — Go/No-Go for Phase 3
| Criterion | Target |
|-----------|--------|
| Synthesis quality | Synthesized solutions rated higher than any individual by ≥2 human evaluators |
| Format variety | All 6 formats tested and working; operator can switch between them |
| Replay fidelity | Replay matches live experience in 5/5 test cases |
| Meta-dataset seeded | 10+ competitions logged with full analytics |
| Operator feedback | 3+ beta operators rate the platform ≥ 8/10 for usefulness |

**Decision maker:** Platform owner + beta operators + advisory board
**Timeline:** End of Week 14

## Phase 3: Spectator + The Forge (Weeks 15–20)

**Objective:** Make competitions shareable and watchable. Build The Forge as an integrated post-arena phase. AI commentary. Public gallery.

### Milestone 3.1 — The Forge Integration (Week 15–16)

- Build Forge orchestrator (post-SYNTHESIZING phase: FORGING → FORGE_COMPLETE)
- Implement Forge solo mode (single agent decomposes winning solution into build artifacts)
- Implement Forge competitive mode (mini-arena: teams compete to produce best implementation plan)
- Build Forge output generators: Implementation Roadmap, Task Graph, Repo Blueprint, API Contracts, Risk Register, Decision Log
- Implement Forge feedback loop schema (track task accuracy, estimate accuracy over time)
- **Deliverable:** After any competition, operator can trigger The Forge to produce build-ready artifacts

### Milestone 3.2 — Spectator Mode (Week 16–18)

- Build spectator authentication (invite links, view-only access tokens)
- Implement spectator Arena View (read-only live lanes, no controls, chat sidebar for discussion)
- Build competition lobby (list of live and upcoming competitions with metadata)
- Implement delayed spectator mode (spectators see events with configurable N-second delay for fairness)
- **Deliverable:** External observers can watch live competitions via invite link

### Milestone 3.3 — AI Commentary (Week 18–19)

- Build commentary generator (post-hoc: analyze event stream, identify key moments, generate narrative)
- Implement live commentary mode (real-time AI narrator providing play-by-play analysis)
- Build highlight reel generator (auto-select pivotal moments, generate condensed summary)
- Implement commentary overlay in replay viewer
- **Deliverable:** Replays and live competitions have AI-generated commentary tracks

### Milestone 3.4 — Public Gallery & Sharing (Week 19–20)

- Build public competition gallery (browse past competitions, view replays, see results)
- Implement shareable URLs for replays and results
- Build competition summary cards (og:image generation for social sharing)
- Implement brief library (browse, fork, re-run community-shared briefs)
- **Deliverable:** Competitions can be shared publicly; gallery attracts inbound interest

### 🚦 Gate 3 — Go/No-Go for Phase 4
| Criterion | Target |
|-----------|--------|
| Forge utility | Teams report Forge outputs save ≥50% of planning time |
| Spectator engagement | Average replay view time ≥ 5 minutes |
| Commentary quality | AI commentary rated useful by ≥70% of viewers |
| Gallery traffic | ≥100 unique visitors to public gallery in first month |

## Phase 4: Platform + Ecosystem (Weeks 21+)

**Objective:** Open API, community, leaderboards, custom model SDK, monetization foundations.

- Build public API for programmatic competition creation (REST + webhooks)
- Create Model Adapter SDK (documentation + template for community model integration)
- Implement leaderboards and model rankings (Elo-style ratings across competitions)
- Build competition templating marketplace (community-contributed briefs with ratings)
- Integrate with CI/CD (trigger architecture review competitions on PR merge)

```
    ↓

    ↓

    ↓

    ↓
Week 12–14: Replay viewer (parallel with synthesis)
    ↓

```

**The make-or-break moment is Week 3** (Gate 0). If the CLI orchestrator produces meaningfully good results from a real competition, everything else is UI and scale. If it doesn't, we need to rethink the orchestration model before investing in infrastructure.

## Risk Register

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| Event normalization across models is harder than expected | High | High | Start with minimal common schema; model-specific fields in metadata. Ship with Claude-only first. |
| Token costs per competition are prohibitive | Medium | High | Governance limits, efficiency scoring, budget alerts. Phase 0 validates cost profile before scaling. |
| Model provider TOS restricts competitive benchmarking | Medium | Medium | Position as "workflow tool" not "benchmark." Self-hosted model option as fallback. |
| Sandbox boot time too slow for good UX | Medium | Medium | Firecracker microVMs boot in <125ms. Pre-warm pool of N sandboxes. |
| Synthesis produces mediocre outputs | Medium | High | Competitive synthesis mode (teams improve on each other) as fallback. Guided mode gives operator control. |
| Single-point-of-failure on event bus | Low | High | NATS JetStream has built-in clustering. Event log is append-only — recoverable from store. |
| Operator doesn't know how to write good briefs | Medium | Medium | Template library, brief quality scorer, example briefs from real competitions. |
| Fairness perception (different model capabilities) | Medium | Low | "Weight class" system, handicaps, or explicitly celebrate asymmetry. |
