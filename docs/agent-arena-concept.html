Concept Architecture — v0.1 Draft

Agent Arena

A competitive orchestration platform where AI agent teams — powered by Claude, Codex, Gemini, and beyond — compete head-to-head on real problems, observed in real time, with automated judging and synthesis of the best ideas into solutions no single model could produce alone.
Audience: Builder-First (Operator as primary user)
Format: Flexible Framework (sprints → deep dives)
Date: March 8, 2026
Status: Concept / Pre-Alpha
01

Vision & Core Thesis

▸
Core Thesis

Adversarial AI workflows produce dramatically better outputs than single-agent workflows. Competition forces divergent thinking. Synthesis of the top competing solutions creates outcomes no individual model could achieve alone. Agent Arena makes this repeatable, observable, and accessible.

Today, when a team needs a strategy, an architecture, or a creative solution, they prompt one AI model and iterate on its single perspective. Agent Arena inverts this: define the problem once, fan it out to competing AI teams, watch them race, judge the results, then synthesize the best elements into a hybrid solution.

The insight came from running a manual AI hackathon — four Claude-powered teams with distinct personas competed on the same brief. The two top solutions each had strengths the other lacked. The final product, synthesized from both, was materially better than either alone. Agent Arena productizes that workflow.

What Makes This Different

Not a chatbot arena
Multi-Step, Not Single-Turn
Chatbot Arena tests single responses. Agent Arena tests entire workflows — research, planning, drafting, revision. Teams spawn sub-agents, use tools, iterate over minutes or hours.
Not a benchmark
Real Problems, Not Standardized Tests
Benchmarks measure capability on fixed tasks. Agent Arena measures performance on YOUR problems — your architecture decisions, your strategy questions, your creative briefs.
Not just scoring
Synthesis, Not Selection
The goal isn't just "which model won." It's "what's the best possible solution combining the top ideas?" The synthesis round is where the real value is created.

The Brief Builder

The brief is the most important input. A structured brief template ensures competing teams get identical, unambiguous instructions. The brief builder guides the operator through defining the problem statement, context documents (uploaded or linked), explicit constraints and non-goals, deliverable format (document, code, architecture, presentation), scoring rubric with weighted criteria, and time budget.

Briefs are versioned and reusable. An operator can run the same brief against different model combinations to compare results, or iterate on the brief itself based on competition outcomes.

03

Competition Lifecycle

▸

Every competition follows a deterministic lifecycle managed by the Orchestrator. The lifecycle is event-driven — each state transition emits events that the front-end, judging engine, and recording system all consume.

// Competition State Machine DRAFT → CONFIGURED → LAUNCHING → RUNNING → TIME_UP → COLLECTING → JUDGING → SCORED → SYNTHESIZING → COMPLETE ↓ PAUSED (operator can pause/resume) ↓ CANCELLED (operator can abort)

State Details

StateDurationWhat Happens
DRAFTUnlimitedOperator writes and refines the brief, configures teams and rules
CONFIGUREDSecondsAll settings locked. Sandboxes being provisioned. Teams allocated.
LAUNCHING5-30sSandboxes spun up, model connections verified, briefs injected. Countdown.
RUNNINGConfig (15m-4h)Teams are working. Events streaming. Clock ticking. Operator observes.
TIME_UP30-60sGraceful shutdown signal. Agents get "wrap up" notification. Final commits.
COLLECTING10-30sDeliverables extracted from each sandbox. Format validated.
JUDGING1-5mJudge panel evaluates all deliverables against rubric. Scores calculated.
SCOREDInstantResults displayed. Rankings revealed. Per-criterion breakdowns available.
SYNTHESIZING2-10mTop solutions fed to synthesis engine. Hybrid solution generated.
COMPLETE—All deliverables, scores, replay data, and synthesis available for export.

Configurable Rules

The operator controls the rules of engagement for each competition. These are set during the DRAFT/CONFIGURED phases:

Visibility
Can Teams See Each Other?
Blind mode: Teams work in isolation. Maximizes divergence. Best for creative/strategy problems. Open mode: Teams can see competitors' progress (read-only). Drives convergence and competitive pressure. Phased: Blind for first 60%, open for final 40%.
Tools
What Can Teams Use?
Tool access is configurable per competition: web search, code execution, file creation, external APIs, database access. Equal tooling ensures fair comparison. Asymmetric tooling tests adaptability.
Personas
Team Identity & Strategy
Each team gets a system prompt "persona" that shapes their approach. Examples: "Conservative enterprise architect" vs. "Move-fast startup CTO" vs. "Academic researcher." Same model, different cognitive frames.
Governance
Resource Limits
Token budgets, API call limits, sub-agent spawn caps, max file count. Prevents runaway costs and ensures teams must be strategic about resource allocation.

Key Components

Orchestrator (The Brain)

The orchestrator is a durable state machine (built on something like Inngest or Temporal) that manages the entire competition lifecycle. It handles sandbox provisioning, brief injection, clock management, pause/resume, graceful shutdown, deliverable collection, and transition between lifecycle phases. It never loses state — if the orchestrator crashes mid-competition, it recovers from the event log and resumes exactly where it left off.

Sandboxes (The Arenas)

Each team runs in a fully isolated sandbox — a lightweight VM (Firecracker microVM or Fly Machine) with a pre-configured environment: CLI tools, language runtimes, file system, and a model adapter. The sandbox exposes a standard interface: receive brief, emit events, produce deliverables. Inside the sandbox, each model's native agentic framework runs — Claude Code for Claude, Codex CLI for OpenAI, Gemini's agent framework for Google. The sandbox adapter normalizes the event stream so the platform sees a consistent format regardless of which model is running.

Event Bus (The Nervous System)

Every action inside every sandbox emits a structured event to a central event bus (NATS JetStream). Events include: agent_spawned, tool_called, file_created, file_modified, reasoning_step, deliverable_submitted, error_occurred. The event bus serves three consumers simultaneously: the live Arena UI (via WebSocket bridge), the event store (for replay), and the analytics engine (for performance tracking). Events are immutable and ordered — the event log IS the source of truth.

Model Adapters (The Translators)

Each model has a different native interface. The adapter layer normalizes this into a common protocol. For Claude: intercepts Claude Code's tool calls and streaming output. For Codex: wraps the Codex CLI agent loop. For Gemini: interfaces with the Gemini agent SDK. The adapter handles brief injection (translating the universal brief format into each model's preferred prompt structure), event emission (mapping model-specific events to the universal event schema), and deliverable extraction (collecting outputs in a standard format).

Architecture Principle

The platform is model-agnostic by design. Adding a new model means writing one adapter — the rest of the platform doesn't change. This is critical for longevity: as new models emerge (Llama, Mistral, Grok, etc.), they can be added as competitors without architectural changes.

Model Cognitive Profiles

▸

Different models don't just have different capabilities — they have different cognitive signatures. Understanding these signatures is key to setting up meaningful competitions and interpreting results.

Thinking styleThorough, analytical, nuancedRapid, implementation-focusedBroad, multimodal, cross-referencing
Strength zoneStrategy, writing, complex reasoningCode generation, rapid prototypingResearch, data synthesis, multimodal

The Meta-Dataset Opportunity

Over hundreds of competitions, Agent Arena builds a unique dataset: which cognitive style wins for which problem type. "For strategic planning, Claude-led teams win 68% of the time. For rapid prototyping, Codex dominates. For problems requiring synthesis of 10+ data sources, Gemini has the edge." This data becomes a decision-support tool: "Based on 247 competitions, for your problem type, we recommend a Claude lead with Codex and Gemini challengers."

Same Model, Different Personas

Competitions don't have to be cross-model. Some of the most interesting results come from pitting the same model against itself with different personas. In the Monday Pulse hackathon, all four teams ran Claude — but "Team PULSE" had an enterprise analyst persona while "Signal Corps" had a military intelligence persona. The cognitive frames produced dramatically different solutions from the same underlying model. Agent Arena supports both cross-model and same-model-different-persona competitions.

06

Competition Formats

▸

The flexible framework supports multiple competition formats. Each format is a configuration preset — same engine, different rules.

⚡ Speed Format
Sprint
15-30 minute rounds. Focused problems with clear deliverables. High energy, fast results. Think speed chess. Great for: API design, code challenges, quick strategy questions, creative briefs.
🏗️ Depth Format
Hackathon
1-4 hour sessions. Complex problems with multi-part deliverables. Teams can spawn dozens of sub-agents, do research, iterate. Think classical chess. Great for: architecture decisions, comprehensive proposals, full product designs.
🔄 Relay Format
Relay Race
Team A works for N minutes, then hands off to Team B (different model) who must continue. Tests interoperability and how well each model understands and extends another's work. Great for: testing model handoff capabilities.
🛡️ Adversarial Format
Red vs. Blue
One team builds, another team tries to break it. Red team / blue team with AI agents on both sides. Alternating rounds of build and attack. Great for: security review, stress testing, finding edge cases.
🏆 Tournament Format
Bracket
Multiple rounds with elimination. 8 teams → quarter-finals → semi-finals → final. Winners advance, losers eliminated. Best for: large-scale competitions with many participants or model variants.
🔬 Lab Format
A/B Experiment
Not a competition — a controlled experiment. Same brief, same model, different configurations (temperature, persona, tool access). Measures the impact of specific variables. Great for: prompt engineering research.
07

Judging & Synthesis

▸

The Judge Panel

Judging uses a multi-judge panel approach to eliminate bias. Each competition has N judges — configurable by the operator. The default panel includes one judge from each competing model family (so no home-field advantage), plus automated scoring on objective criteria.

Judge TypeRoleWhen Used
AI Cross-JudgeModel A judges Model B's work. Eliminates self-scoring bias.Always (default)
AI Neutral JudgeA model not competing in this round acts as impartial evaluator.When 3+ models available
Automated ScorerObjective tests: code compiles, documents validate, math checks out.When deliverables are testable
Human JudgeOperator or invited reviewers score manually. Can override AI judges.Operator opt-in

Scoring uses a weighted rubric defined in the brief. Example criteria: correctness (30%), creativity (20%), completeness (20%), feasibility (15%), presentation (15%). Each judge scores each criterion independently. Final scores are averaged with outlier detection — if one judge scores dramatically differently from the others, it's flagged.

The Synthesis Engine

This is Agent Arena's killer feature and what separates it from a simple "model comparison tool."

After judging, the synthesis engine takes the top 2-3 solutions and creates a hybrid that combines the best elements of each. The synthesis process is transparent: it identifies which specific ideas, sections, or approaches it's pulling from each solution and why. The output is a new deliverable — not a summary, but a fully realized solution that's materially better than any individual submission.

Synthesis Modes

Auto-Synthesis: The platform's synthesis agent automatically combines top solutions. Fast, consistent, good for sprints.

Guided Synthesis: The operator selects which elements to combine. More control, better for complex problems where domain expertise matters.

Competitive Synthesis: Each remaining team is given the other top solutions and asked to produce an improved hybrid. A second round of competition on the synthesis itself.

Replay System

Every competition can be replayed at variable speed — 1x, 2x, 4x, 10x. The replay viewer reconstructs the exact visual state at any point in time from the event stream. Operators can scrub to any moment, pause, zoom into a specific team's activity, and see what every agent was doing at that exact timestamp. Replays are shareable via URL — this is the foundation for the spectator experience in later versions.

Commentary Track (Future)

An AI narrator can generate a "commentary track" for replays — explaining what each team's strategy was, calling out pivotal moments ("At 3:42, Team Beta made a critical architectural decision that ultimately won them the round"), and providing expert analysis. Think sports commentary for AI competitions.

Build Roadmap

▸
Phase 0 — Foundation (Weeks 1-3)
CLI Orchestrator + Single Model
Build the core competition engine as a CLI tool. One model (Claude), two competing teams with different personas, structured brief input (JSON/YAML), event logging to file, basic judging with rubric scoring. No UI — terminal output only. This validates the orchestration logic and event system. Essentially productizing what you did manually for The Monday Pulse.
Phase 1 — Multi-Model + Web UI (Weeks 4-8)
Add Codex + Gemini, Build Arena View
Write model adapters for Codex and Gemini. Build the React Arena UI with live lane view, WebSocket streaming, and basic replay. Add sandbox isolation (Docker initially, Firecracker later). Build the brief builder with template library. This is the first version where you can watch AI teams compete in real time from a browser.
Phase 2 — Synthesis + Formats (Weeks 9-14)
The Intelligence Layer
Build the synthesis engine. Implement the multi-judge panel. Add competition format presets (sprint, hackathon, relay, red/blue). Build the replay viewer with timeline scrubbing. Add performance analytics dashboard. This is where Agent Arena becomes genuinely valuable — not just showing who won, but creating solutions better than any individual submission.
Phase 3 — Spectator + Sharing (Weeks 15-20)
The Audience Layer
Shareable replay URLs. Spectator mode (view-only access to live competitions). AI-generated commentary tracks. Competition highlights and summaries. Public competition gallery. This is where the platform starts generating content that can attract an audience beyond operators.
Phase 4 — Platform + Community (Weeks 21+)
Ecosystem Expansion
Public API for programmatic competition creation. Community brief library (shareable, forkable briefs). Leaderboards and model rankings. Custom model adapter SDK for bringing any model into the arena. Integration with CI/CD for automated architecture review competitions. This is where the flywheel starts — more competitions generate more data, better analytics attract more operators, more operators generate more competitions.

The Forge — Arena to Execution

▸
The Gap

Arena competitions produce brilliant proposals and designs — the what and the why. But a team that opens those documents Monday morning still can't start building. They need task breakdowns, repo scaffolds, dependency graphs, and acceptance criteria. The Forge bridges arena output to execution.

The Forge is an optional post-arena phase that consumes the winning or synthesized solution and produces actionable build artifacts. It can run as a single-agent decomposition or — staying true to the arena philosophy — as its own competitive round where teams race to produce the best implementation plan from the same winning solution.

Extended Lifecycle

// Standard Arena lifecycle ... → SCORED → SYNTHESIZING → COMPLETE // With The Forge enabled ... → SCORED → SYNTHESIZING → FORGING → FORGE_COMPLETE ↓ Forge Mode: competitive → runs a mini-arena Forge Mode: solo → single-agent decomposition Forge Mode: guided → operator picks elements

Output Tiers

The Forge produces three tiers of deliverables, each building on the previous:

TIER 1
Arena Outputs
Proposal, technical design, strategic rationale. "Convince stakeholders" artifacts.
TIER 2
Forge Outputs
Implementation plan, task graph, repo blueprint, API contracts. "Start building Monday" artifacts.
TIER 3
Launchpad
Working code scaffolds, CI/CD configs, deployed previews. "Already started" artifacts.

Tier 2 — Forge Deliverables (Detail)

ArtifactFormatPurpose
Implementation Roadmap Structured Markdown Phases, milestones, dependencies, go/no-go gates. The narrative backbone of execution. Translates the "why" into sequenced "when."
Task Graph JSON + Markdown Every task with ID, description, acceptance criteria, effort estimate, dependencies, skill type. Importable into Jira, Linear, GitHub Projects.
Repo Blueprint Directory tree + stubs Full project structure, key file stubs with purpose comments, package manifests with dependencies, environment templates (.env.example), Docker/compose configs.
API Contracts OpenAPI / GraphQL SDL Service interfaces derived from the technical design. Enables parallel frontend/backend development from day one.
Risk Register Markdown table Risks with probability, impact, mitigation, and owner. Seeded from competing teams' critiques of each other — the arena naturally surfaces blind spots.
Decision Log ADR format Architecture Decision Records capturing every significant choice, alternatives considered, and rationale. Prevents re-litigating decisions during build.

Forge Feedback Loop

Once a Forge output is being executed — people are actually building from it — the platform can track which tasks were accurate vs. needed rework, which estimates were close vs. wildly off, which dependencies were correctly identified vs. missed. This execution feedback feeds into the meta-dataset, making future Forge outputs better. Over time: "Claude estimates average 1.3x actual effort. Codex repo scaffolds need 30% fewer modifications than Gemini-generated ones."

Proof of Concept

The Monday Pulse hackathon produced a Proposal and Technical Design through competitive arena-style generation. Those documents were then fed through a Forge prototype to produce an Implementation Roadmap, Task Graph, and Repo Blueprint — demonstrating the full arena-to-execution pipeline on a real project.

Open Questions & Risks

▸
⚠️ Technical Risk
Event Normalization Across Models
Claude Code, Codex CLI, and Gemini's agent framework emit fundamentally different event types. Normalizing these into a universal schema without losing model-specific nuance is the hardest technical challenge. Start with a minimal common schema and extend per-model.
⚠️ Cost Risk
Token Budget Per Competition
A 4-team, 2-hour hackathon with aggressive sub-agent spawning could consume millions of tokens. Clear governance limits, budget visualization, and "efficiency scoring" (rewarding teams that achieve more with fewer tokens) help manage this.
⚠️ Fairness Risk
Apples-to-Oranges Comparisons
Models have different context windows, tool capabilities, and latencies. Is it fair to compare Claude (200K context) vs. a model with 32K? Need clear "weight classes" or handicap systems. Or lean into it — asymmetric capability IS the point.
⚠️ Platform Risk
API Access & Rate Limits
Running multiple concurrent agentic sessions against multiple model providers means navigating different rate limits, pricing tiers, and TOS. Some providers may restrict competitive benchmarking. Need solid relationships or self-hosted model options.
❓ Open Question
What's the Right Naming?
"Agent Arena" is the working title. Alternatives: The Colosseum, AgentOlympics, BattleGround, The Forge, The Crucible, Clash. The name should convey competition, intelligence, and the seriousness of the outputs — not just gaming entertainment.
❓ Open Question
Open Source or Proprietary?
Open-sourcing the orchestration engine could drive adoption and community contributions. Proprietary synthesis + analytics could be the monetization layer. Hybrid approach: open core with premium intelligence features.
