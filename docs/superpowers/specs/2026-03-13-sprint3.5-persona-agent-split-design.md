# Sprint 3.5 — Persona + Agent Split Design

## Overview

Redesign the Agent Armory to properly separate **Agents** (the body — provider, model, options) from **Personas** (the mind — system prompt, strategy, purpose). Both live in the DB. Personas are reusable across agents and providers. The Armory becomes a 3-tab interface: Roster, Personas, Agent Builder.

---

## Core Concept

> **Agent = Body. Persona = Mind.**

- A **Persona** is a provider-agnostic system prompt template. The same "architect" mind can run on Claude, Codex, or Gemini.
- An **Agent** is a runnable body+mind combo: a specific provider + model + persona reference, with its own battle stats.
- **Stats live on Agents** — Claude+architect and Codex+architect earn separate win/loss records.
- **Personas are shared** — many agents can reference the same persona. Editing a persona updates all agents that use it.

## Data Model

### `personas` table (NEW)

| Column | Type | Notes |
|---|---|---|
| `id` | text PK | e.g. `persona-architect` |
| `name` | text NOT NULL | unique among non-retired |
| `description` | text | one-line summary |
| `systemPrompt` | text NOT NULL | injected at battle start |
| `avatar` | text | emoji |
| `tags` | text[] | |
| `createdBy` | text | `'system'` \| user id |
| `retired` | boolean | default false |
| `createdAt` | timestamp | |
| `updatedAt` | timestamp | |

**Unique constraint:** Implemented as a Drizzle partial index:
```ts
uniqueIndex('personas_name_active_unique').on(table.name).where(sql`retired = false`)
```
Not a column-level unique — retired personas do not block name reuse.

**System seed (9 personas):**
- Claude archetypes (7): `architect`, `speedrunner`, `pragmatist`, `researcher`, `adversarial`, `defender`, `pioneer`
- Cross-provider (2): `standard` (for Codex), `standard-gemini` (for Gemini)

System personas (`createdBy: 'system'`) are **view-only** in this sprint — no edit, no retire, no fork in UI. Persona fork is Sprint 4.

### `agents` table (replaces `agent_profiles`)

| Column | Type | Notes |
|---|---|---|
| `id` | text PK | |
| `name` | text NOT NULL | |
| `personaId` | text FK → personas.id | SET NULL on persona retire/delete |
| `provider` | `'claude'\|'codex'\|'gemini'` | NOT NULL |
| `modelVariant` | text NOT NULL | e.g. `claude-sonnet-4-6` |
| `providerOptions` | jsonb | future: temperature, etc. (schema only, no UI this sprint) |
| `createdBy` | text | `'system'` \| `'auto'` \| user id |
| `forkedFromId` | text FK → agents.id | self-referential, SET NULL |
| `retired` | boolean | default false |
| `statsWins` | integer | default 0 |
| `statsLosses` | integer | default 0 |
| `statsTotal` | integer | default 0 |
| `statsAvgScore` | numeric | weighted running average |
| `statsLastUsedAt` | timestamp | |
| `createdAt` | timestamp | |
| `updatedAt` | timestamp | |

**Unique constraint:** Drizzle partial index:
```ts
uniqueIndex('agents_provider_name_active_unique').on(table.provider, table.name).where(sql`retired = false`)
```

**`createdBy` values:**
- `'system'` — seeded at startup, Fork only in UI (no Edit/Retire)
- `'auto'` — auto-created from a CLI/API provider+persona string pair (see Auto-Save Rule below)
- user id — user-created, full CRUD

**Retiring a persona:** The retire endpoint must check if any non-retired agents reference the persona. If so, return `409 Conflict: "N agents still use this persona — retire or reassign them first."` This prevents agents with `personaId = NULL` from running with no system prompt.

**System seed (9 agents):**
- `claude` × 7 (architect, speedrunner, pragmatist, researcher, adversarial, defender, pioneer)
- `codex:standard`
- `gemini:standard-gemini`

### `competitions.teams` jsonb shape (updated)

The `teams` jsonb on the competitions table is updated to include `agentId` alongside the existing string fields:

```ts
interface Team {
  id: string;          // team slot id (team-a, team-b)
  agentId?: string;    // FK to agents.id — set when battle launched from UI
  provider: string;    // 'claude' | 'codex' | 'gemini'
  model: string;       // provider string e.g. 'claude'
  persona: string;     // persona name — kept for display + backward compat
  modelVariant?: string;
}
```

`agentId` is optional to preserve backward compatibility with competitions created before Sprint 3.5.

## Agent Armory — 3-Tab UI (`/agent-armory`)

### Tab 1: Agent Roster

Read-heavy gallery. The "character select" screen.

- Filter pills: All / Claude / Codex / Gemini
- Search input: filter by name or tags
- Agent cards show: avatar, name, provider badge, persona name, stats (W/L/avg)
- Actions per card:
  - **System agents (`createdBy: 'system'`):** Fork only. Forking a system agent creates a new user-owned agent pointing to the **same persona** — the persona is not copied. Persona fork is Sprint 4.
  - **Auto/user agents:** Edit → goes to Builder pre-filled, Fork → goes to Builder as fork, Retire
- "+ New Agent" button → navigates to Builder tab (blank)
- Retired agents in collapsed `<details>` at bottom

### Tab 2: Personas

Template library. The "mindset workshop".

- Grid of persona cards
- Persona card shows: avatar, name, description excerpt, tags, "used by N agents" count (fetched via `GET /personas/:id` or included in list response)
- Actions:
  - **System personas:** view/expand only — no edit, retire, or fork this sprint
  - **User personas:** Edit (opens inline form on the tab), Retire (blocked if active agents reference it — show count)
- "+ New Persona" button → opens inline creation form on the Personas tab
- Persona creation/edit form fields: name, description, system prompt (textarea), avatar (emoji picker), tags

**AI Assist — two entry points:**
1. **"✨ Generate full persona"** button at top of form — user enters a freeform idea string → hits ✨ → calls `POST /generate-persona` with `{ mode: 'full', idea: string }` → response pre-fills all fields. User edits and saves.
2. **✨ button on the system prompt field** — calls `POST /generate-persona` with `{ mode: 'expand', systemPrompt: string }` → returns improved prompt text, replaces field value. User edits and saves.

### Tab 3: Agent Builder

Character creator. Create new agents or edit existing ones. Navigated to from Roster (Edit/Fork/New Agent).

**Fields:**
1. **Persona (mind)** — searchable dropdown from Personas library (avatar + name). Selecting one populates a read-only preview of the system prompt. "+ Create new persona inline" expands a panel (same form as Personas tab, including AI assist) — user creates the persona without leaving the Builder, then it appears in the dropdown automatically.
2. **Provider (body)** — Claude / Codex / Gemini pill selector
3. **Model Variant** — dropdown populated by provider: Claude → [claude-sonnet-4-6, claude-opus-4-6, claude-haiku-4-5], Codex → [codex-standard], Gemini → [gemini-2-flash]
4. **Agent Name** — text input
5. **Avatar** — emoji picker (optional — defaults to persona's avatar if blank)
6. **Tags** — comma-separated

**Modes:**
- **Create** — blank form, "Save Agent" button → `POST /agents`
- **Edit** — pre-filled, "Update Agent" button → `PATCH /agents/:id`
- **Fork** — pre-filled from source agent, `forkedFromId` set, name pre-suffixed with `my-`, "Save Fork" button → `POST /agents/:id/fork`

**⚠ Complexity note:** The inline persona creation panel inside Builder is intentional (explicitly requested) — it is the same component as the Personas tab form, reused. Implement as a shared `<PersonaForm>` component to avoid duplication.

## Battle Setup — Step 3 Changes (`/competitions/new`)

Step 3 replaces the hardcoded `PERSONAS` array with DB-sourced agent chips.

**New flow:**
1. Provider pills (Claude / Codex / Gemini) — same as today
2. **Search input** — filters agent chips by name as user types (client-side filter on loaded list)
3. **Agent chips** — all non-retired agents for the selected provider, fetched on step entry via `GET /api/agents?provider=claude&retired=false`. Response includes nested `persona: { name, avatar }` to avoid a second fetch. Chips show `agent.persona.avatar + agent.name`.
4. **"+ Go to Armory"** link → opens `/agent-armory` in a new tab (or navigates with `?tab=builder`)

**Team data stored:**
```ts
{ id: 'team-a', agentId: 'agent-claude-architect', provider: 'claude', model: 'claude', persona: 'architect', modelVariant: 'claude-sonnet-4-6' }
```

**Auto-Save Rule (CLI / legacy API path only):**
The UI always selects a known agent by `agentId`. Auto-save applies only when `POST /competitions` receives `{ provider, persona }` string pair (no `agentId`) — this is the CLI and backward-compat API path. In that case, the server:
1. Looks up `agents` by `(provider, personaId)` where `persona.name = personaName` and `agent.retired = false`
2. If found → use its `agentId`
3. If not found → create agent with `createdBy: 'auto'`, name = `personaName`, linked to the persona

**Runtime wiring — two resolution paths:**

```
New UI path (agentId present):
  agentRepo.getById(agentId) → personaRepo.getById(agent.personaId) → persona.systemPrompt → injectBrief

Legacy/CLI path (provider + persona string, no agentId):
  agentRepo.getByProviderAndPersonaName(provider, personaName)
    → found: use agent.personaId → personaRepo.getById → systemPrompt → injectBrief
    → not found: auto-create agent → then same chain
    → DB unavailable: resolvePersona() from claude-personas.ts (hardcoded fallback)
```

**Stats update wiring:**
After `SCORED` state, `competition-runner.ts` calls `agentRepo.incrementStats(agentId, { won: boolean, score: number })` for each team. The `agentId` is stored on the competition record (in `teams` jsonb) so the post-score callback can find it. For auto-created agents, the `agentId` is stored immediately upon creation.

## `POST /generate-persona` — Endpoint Contract

**Request:**
```ts
{ mode: 'full';   idea: string }         // generate everything from scratch
{ mode: 'expand'; systemPrompt: string } // improve an existing system prompt
```

**Response:**
```ts
// Full mode — all fields returned
{ name: string; description: string; systemPrompt: string; tags: string[]; avatar: string }

// Expand mode — only systemPrompt returned
{ systemPrompt: string }
```

Rate limit: 20/min (same limiter as `generate-brief`).

## `GET /agents` — Query Parameter Contract

| Param | Type | Default | Notes |
|---|---|---|---|
| `provider` | `'claude'\|'codex'\|'gemini'` | — | filter by provider |
| `retired` | `boolean` | `false` | `"false"` string parsed to boolean |
| `search` | `string` | — | filter by name prefix (case-insensitive) |

**Response:**
```ts

```

Persona fields are JOINed server-side to avoid N+1 calls in the UI.

## Migration Strategy (`0009_personas_agents.sql`)

Migration steps — order matters:

1. **Create `personas` table** with partial unique index
2. **Insert system personas** (9 rows) — use `INSERT ... ON CONFLICT DO NOTHING` to be idempotent against re-runs
3. **Create `agents` table** with `personaId` FK → personas, partial unique index
4. **Migrate `agent_profiles` rows:**
   - For each row, find the matching persona by name in the new `personas` table
   - If found → insert into `agents` with `personaId` set
   - If not found → insert a new persona row first, then the agent row
   - Deduplicate by persona name (multiple agents with the same persona name map to one persona row)
5. **Drop `agent_profiles`**

The migration is idempotent where possible. The Sprint 3 system-seeded `agent_profiles` rows (9 rows: 7 claude + codex:standard + gemini:standard-gemini) map 1:1 to the 9 system agents/personas.
